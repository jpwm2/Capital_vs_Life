 0. 最初に：config.toml が「読めなかった」件
================================================================================
C:/Gitlab-Runner/config.toml の中身は取得できませんでした。

理由：
  このセッションはクラウド上の Linux コンテナで動いており、Runner が稼働している
  Windows マシン (G23R0480C) とはネットワーク的に一切つながっていません。
  C: ドライブは存在せず、GitLab API にも config.toml を返すエンドポイントはありません。
  ファイルを読むには当該 Windows 上でコマンドを実行する必要がありますが、それには
  ci 配下の YAML/スクリプト追加・変更が必須で、今回の制約（ci配下は閲覧のみ、
  スクリプト変更禁止）に反するため実施していません。

代わりに行ったこと：
  ジョブログ330件の挙動から config.toml の主要設定を逆算しました（第4章）。
  concurrent と limit については、8時間分の全ジョブの開始/終了時刻を突き合わせた
  実測なので、値としてはほぼ確定的です。
  第4章の末尾に「手元で確認していただきたい項目リスト」を付けています。

 --- 実測で確定している値 ---------------------------------------------------
 concurrent = 4                                                        [PERF]
   根拠: 8時間・330ジョブの開始/終了時刻を突き合わせた結果、このマシン上で
         同時に走ったジョブ数の最大は「ちょうど4」。5以上は一度もなし。
         観測された内訳:
            Runner1×4                   … 69秒間
            Runner1×3 + Runner2×1       … 155秒間
            Runner1×3                   … 3214秒間
            Runner1×2 + Runner2×1       … 908秒間  ほか

 [[runners]] Runner2 (ID 52680622) の limit = 1                        [PERF]
   根拠: 全123ジョブを通じて同時実行数が2になった瞬間が一度もない。
         さらに Runner2 で30秒以上待たされたジョブ41件のうち36件は、
         マシン全体のジョブ数が3以下（＝concurrent=4に余裕がある）状態で
         待たされていた。よって concurrent ではなく Runner2 自身の
         limit=1 が原因と断定できます。
         実測の待ち時間: create-testcases-from-model 最大 634秒、
                         btob-test 最大 413秒、create-harness-model 最大 265秒。

 [[runners]] Runner1 (ID 53049374) の limit >= 4（おそらく 4 または 0=無制限）
   根拠: 同時4本の実行を観測。

    なく全クローンになります。                                          [PERF]

 --- 読めていない＝手元で確認していただきたい項目 ---------------------------

 順に並べています。

   2. concurrent                    ← 4 かどうかの確認

   6. output_limit                  ← ログ上限(既定4096KB)
   7. request_concurrency           ← 既定1
   8. shell = "powershell" の明示有無
   9. environment = [...]           ← Runner側で環境変数を注入しているか
  10. [runners.feature_flags]       ← FF_ 系の設定有無
  11. session_server / listen_address
  12. log_level / log_format

 8. [PERF] パフォーマンスに効く項目まとめ（影響が大きい順）
================================================================================
 (1) Runner2 の limit = 1  ―― 最大のボトルネック
     create-harness-model と btob-test が1本ずつしか流れない。実測で最大
     634秒の待ち。複数パイプラインが並ぶと待ち時間が加算的に伸びる。
     config.toml の該当 [[runners]] の limit を上げるのが最も効果が大きい。
     ただし (2) の制約に注意。

 (2) Runner1 と Runner2 が同一マシン（system ID s_d6d5e28bfc7f）
     limit を上げても CPU / メモリ / ディスク / MATLABライセンスを
     奪い合うため、素直にスループットが倍にはならない。
     paused の予備Runner 2台（53424454 / 53424522）を別マシンで再開する方が
     筋が良い。

 (3) 5ジョブが完全直列 + 実行Runnerが交互
     R1→R1→R2→R1→R2 と行き来するため、ジョブごとに
     「git fetch + 成果物DL + MATLAB起動 + MATLAB終了 + 成果物UL」の
     固定費 約37秒 を毎回払っている（合計 約185秒 / 全体の31%）。
     特に guideline-check（193秒）は create-harness-model を
     ブロックしているが、成果物を渡していない（needs に artifacts 指定なし）。

 (4) MATLAB を5回別々に起動している（起動39.7秒 + 終了52.3秒 = 92秒）
     終了処理が DNS 解決待ちで長い。診断ジョブの実測では
     wpad / www.mathworks.com / udc-service.mathworks.com の解決に
     20〜30秒かかっている。
     - MathWorks ServiceHost の DDUX テレメトリが有効（isDduxEnabled: true）
     - wpad は名前解決に失敗し続けている（WPAD自動検出が無効化されていない）
     これらを止める / hosts か NO_PROXY で潰すだけで1ジョブ数秒〜十数秒短縮。

 (5) GIT_CLEAN_FLAGS = "-ffdx -e /Workspace/"
     Workspace 以外は毎回全消しになるため、実際のログで
        Removing models/M_DrvDreBat0/slprj/
        Removing models/M_DrvDreBat0/M_DrvDreBat00.slxc
     が毎ジョブ発生している。Simulink のビルドキャッシュ（slprj / .slxc）が
     毎回破棄され、フルリビルドになっている。ここは伸びしろが大きい。

 (6) 作業コピーが分散している
     decide-targets と guideline-check だけ GIT_CLONE_PATH 未設定のため
     デフォルトパス（スロット番号ごとに別ディレクトリ）を使う。
     concurrent=4 だと Runner1 上に最大8個のリポジトリ作業コピーができ、
     初回のスロットでは fetch ではなく全クローンになる。
     全ジョブで GIT_CLONE_PATH を揃えると、fetch 差分が効いて安定する。

 (7) auto_cancel_pending_pipelines = disabled かつ interruptible 未設定
     連続 push すると古いパイプラインが最後まで走り続け、
     limit=1 の Runner2 を占有する。当日80件超のパイプラインが流れており、
     影響は小さくない。

 (8) Windows Defender / Defender for Endpoint が常駐
     C:\GitLab-Runner\b1, b2 配下と MATLAB のビルド出力（slprj など）は
     大量の小ファイル生成を伴うため、リアルタイムスキャンの除外設定が
     入っていないと数十%単位で遅くなる。除外設定の有無は要確認。

 (9) ci_default_git_depth = 20 / build_git_strategy = fetch
     現状 get_sources は6〜7秒で収まっており、ここは問題なし。

 (10) matlab_utf8.ps1 がMATLAB出力を全バッファ
     速度そのものへの影響は小さいが、MATLAB実行中はログが一切流れないため
     長いジョブの進捗が見えず、ハングとの区別がつかない。

 (11) MAX_TESTCASES_GENERATION_TIME = 300
     テストケース生成の上限時間。create-testcases-from-model の
